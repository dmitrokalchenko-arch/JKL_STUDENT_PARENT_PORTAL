# Бизнес-правила

Раздел находится в стадии наполнения. Здесь фиксируются согласованные
бизнес-правила модуля JKL Club по мере их появления.

## Актуальные правила — концепция семейного аккаунта

Полное архитектурное описание — в
`docs/architecture/FAMILY_ACCOUNT_CONCEPT.md`.

1. Один семейный аккаунт может быть связан с одним или несколькими
   учениками.
2. Один ученик должен быть связан как минимум с одним семейным аккаунтом,
   если семейный доступ активирован.
3. Семья выбирает активного ребёнка после входа.
4. Все детские разделы показывают данные только выбранного ребёнка.
5. Переключение ребёнка должно обновлять все блоки страницы.
6. Родитель, опекун и ребёнок могут использовать общие данные входа
   семейного аккаунта.
7. Отдельные аккаунты родителей и детей на первом этапе не создаются.
8. Тренеры имеют отдельную авторизацию.
9. Тренер может видеть только учеников, доступных ему по правилам клуба.
10. Тренер может видеть договор и статус оплаты ученика.
11. Полные банковские реквизиты и чувствительные платёжные данные тренеру
    не показываются.
12. Удаление ребёнка из семьи не должно удалять запись ученика из основной
    базы.
13. Добавление ребёнка в семью означает создание связи, а не копирование
    данных ученика.
14. Один ученик не должен дублироваться для разных семейных представлений.
15. Основным источником данных ученика остаётся существующая таблица
    `students` основной базы JCL Club.
16. Семейный аккаунт не должен создавать вторую таблицу-дубликат `students`.
17. Данные групп, посещаемости, клубов и тренеров не дублируются.
18. Все будущие права доступа должны учитывать `club_id`.
19. Перед реализацией требуется отдельное согласование RLS-политик.
20. Финансовые данные семьи нельзя путать с SaaS-платежами клуба платформе
    JCL (см. `docs/database/EXISTING_DATABASE_AUDIT.md`, находка про
    `clubs.contract_*` и `club_payments`).

## Утверждённые решения — вход, привязка и договор (детализация)

Пользователь подтвердил следующие решения — они дополняют правила 1–20 и
закрывают ранее открытые вопросы (полный контекст — в
`docs/architecture/FAMILY_ACCOUNT_CONCEPT.md`, раздел 15):

21. Семейный аккаунт создаёт клуб — семья не может зарегистрироваться
    самостоятельно.
22. Вход в семейный аккаунт выполняется по уникальному нику семьи; email
    используется только для восстановления пароля.
23. Семья может самостоятельно менять общий пароль после входа.
24. **Обновлено 2026-09-24 (продуктовое решение, см. migration
    20260924100069):** ребёнок может быть одновременно связан максимум с
    **одним** активным семейным аккаунтом. Даже при раздельно проживающих
    родителях используется ОДИН общий Familienkonto с общими данными входа,
    а не два отдельных аккаунта. Один семейный аккаунт по-прежнему может
    содержать любое число детей (см. правило 1) — ограничение только на
    число активных семей у ОДНОГО ребёнка.
25. Добавление второго родителя/опекуна отправляется как запрос и
    подтверждается клубом — так же, как и привязка ребёнка (правило 5 в
    старой нумерации выше это уже задавало для ребёнка; теперь то же самое
    подтверждено и для опекуна).
26. Договор относится к конкретному ребёнку (`student_id`), а не к семье в
    целом.
27. У разных детей одной семьи могут быть разные тарифы, даты начала
    договора, сроки оплаты и условия договора.
28. Тренер видит по ученику: статус договора, дату, до которой оплачено,
    наличие задолженности, следующий срок оплаты.
29. Тренер не видит банковские реквизиты, платёжные токены и чувствительные
    данные способа оплаты ни при каких условиях.
30. Тренер не может изменять платежи и финансовые операции — доступ к
    финансовому блоку у тренера только на чтение (см. концептуальное
    представление `trainer_student_finance_summary` в
    `docs/database/FAMILY_ACCOUNT_DATA_MODEL_DRAFT.md`).

## Членство ребёнка в Familienkonto (добавлено 2026-09-25, обновлено 2026-09-26; migration `20260924100069`/`20260925100070`/`20260926100071`)

31. «Удаление ребёнка из семьи» (Kind entfernen) означает перевод связи
    `family_students` из `active` в `suspended` — НЕ удаление строки, НЕ
    удаление ученика. История связи сохраняется.
32. Ученик может иметь **0 или 1** активный Familienkonto (никогда больше
    одного). Ноль активных Familienkonto — валидное, ожидаемое состояние
    ученика, не ошибка. Такой ученик может позже: быть добавлен в другой
    уже существующий Familienkonto; быть возвращён в прежний Familienkonto
    (реактивация приостановленной связи); получить собственный новый
    Familienkonto.
33. Student Page ученика (`student_page_access`, подписка, `accessUntil`,
    `manualDisabled`, прогресс по техникам, история) принадлежит
    `student_id` и переживает ЛЮБЫЕ изменения принадлежности к
    Familienkonto без исключений — включая истечение подписки: истёкшая
    Student Page подписка НЕ отвязывает ученика от Familienkonto и не
    влияет на членство никак.
34. Создание отдельного (независимого) Familienkonto для ранее привязанного
    ребёнка — всегда явное решение Super Admin. Никакой автоматической
    логики (в частности, по возрасту) не существует и не планируется.
35. **Обновлено 2026-09-26 (уточнение продуктового решения, migration
    `20260926100071`):** уже существующий Familienkonto обязан содержать
    **минимум одного** активного ребёнка. Удаление ПОСЛЕДНЕГО активного
    ребёнка через `remove_family_student` **отклоняется** сервером
    (`cannot_remove_last_student`) — связь остаётся активной, ничего не
    меняется. Если у ребёнка, являющегося единственным в своей семье,
    нужны независимые данные входа — для этого используется существующее
    управление логином/email/паролем ЭТОГО ЖЕ Familienkonto (`set_login`/
    `set_contact_email`/`set_password`), а не перенос в новый пустой
    аккаунт.
36. Одновременные (параллельные) запросы на удаление разных детей одной
    семьи не могут привести семью к 0 активным детям — гарантируется на
    уровне базы данных через блокировку строки семьи внутри
    `remove_family_student_link()` (не только проверкой во frontend/Edge
    Function).

Дополнительные бизнес-правила (расчёт рейтинговых баллов, условия допуска
к экзамену и т.д.) будут добавлены по мере согласования с пользователем.

## Общее правило (сохраняется)

- Не создавать вымышленные данные базы без отдельного согласования
  (см. `.claude/CLAUDE.md`).

## Заменено новым решением (архив, сохранено для истории)

Ранее действовавшие правила:

- «Студент не должен видеть платежи и договоры.»
- «Платежи и договоры относятся только к кабинету родителя.»

Эти правила **заменены** правилами 6–7 и 9–11 выше: в семейном аккаунте
раздел «Договор и оплата» видят все, кто вошёл под общим семейным логином
(включая ребёнка, если он знает данные входа). Разграничение теперь идёт не
между «студентом» и «родителем», а между семейным доступом и тренерским
доступом (тренер видит статус оплаты, но не банковские реквизиты — правило
11).
