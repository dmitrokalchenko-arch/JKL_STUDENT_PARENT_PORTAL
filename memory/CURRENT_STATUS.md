## Смена концепции — единый семейный аккаунт

- Название проекта остаётся `JKL_STUDENT_PARENT_PORTAL` — не меняется.
- Отдельные Student Portal и Parent Portal как два независимых интерфейса
  **больше не проектируются**.
- Утверждена концепция единого семейного аккаунта (Family Account) — полное
  описание в `docs/architecture/FAMILY_ACCOUNT_CONCEPT.md`.
- Семья может иметь одного или нескольких детей, привязанных к одному
  аккаунту.
- Добавляется раздел «Моя семья» — показывает всех привязанных детей,
  позволяет выбрать активного ребёнка.
- Предусматривается добавление второго родителя или опекуна к семейному
  аккаунту.
- Предусматривается управление семейным аккаунтом (отдельный блок/раздел).
- Семья использует общий логин/ник и пароль — один аккаунт на всю семью.
- Отдельные логины детей и родителей на первом этапе не создаются.
- Тренер использует отдельный вход, независимый от семейного аккаунта.
- Тренер сможет просматривать страницы доступных ему учеников, договор и
  статус оплаты (без чувствительных банковских реквизитов).
- Старые документы (`memory/PRODUCT_VISION.md`, `memory/BUSINESS_RULES.md`,
  `memory/UI_RULES.md`, `docs/SCREEN_REGISTRY.md`) обновлены: прежняя
  концепция раздельных кабинетов сохранена в них как архив и явно помечена
  «Заменено новым решением» / «Заменено единой концепцией Family Account».
- Создан черновик модели данных `docs/database/FAMILY_ACCOUNT_DATA_MODEL_DRAFT.md`
  (6 новых сущностей: `family_accounts`, `family_students`,
  `family_guardians`, `family_link_requests`, `family_contracts`,
  `family_payments`) — без SQL, только концепция, привязанная к
  существующей таблице `students` из `JCL_Gruppen`.
- База данных и код **не изменялись**. SQL, миграции, package.json,
  HTML/CSS/JS/TS, компоненты, Supabase Client и RLS-политики не создавались.

## Утверждённые решения семейного аккаунта

Пользователь подтвердил все ранее открытые вопросы семейного аккаунта.
Полный список из 17 пунктов зафиксирован в
`docs/architecture/FAMILY_ACCOUNT_CONCEPT.md` (раздел 15, «Утверждённые
решения»), детализирован в `memory/BUSINESS_RULES.md` (пункты 21–30) и
отражён в `memory/PRODUCT_VISION.md`. Ключевое:

- Семейный аккаунт создаёт клуб; вход — по уникальному нику семьи; email —
  только для восстановления пароля; смена пароля — самостоятельно.
- Добавление ребёнка и добавление второго родителя/опекуна — оба через
  запрос, подтверждаемый клубом.
- Один ребёнок может быть связан максимум с ОДНОЙ активной семейной
  записью (обновлено 2026-09-24 — прежде было максимум 2, см.
  `memory/BUSINESS_RULES.md` правило 24).
- Договор привязан к конкретному ребёнку, у разных детей одной семьи могут
  быть разные тарифы и условия.
- Тренер видит статус договора, дату оплаты «до», наличие задолженности и
  следующий срок оплаты; не видит банковские реквизиты, токены и
  чувствительные платёжные данные; не может изменять платежи.
- Открытые вопросы авторизации, связи детей и тренерского финансового
  доступа — **закрыты**. Технические детали (конкретный механизм
  хеширования пароля/Auth, алгоритм отбора учеников для тренера, провайдер
  оплаты) сознательно отложены до выбора технического стека — это не
  архитектурные вопросы.
- Модель данных уточнена в
  `docs/database/FAMILY_ACCOUNT_DATA_MODEL_DRAFT.md`: добавлено
  концептуальное представление `trainer_student_finance_summary` для
  тренера (только чтение, без банковских данных).

## Trainer Auth — финальный review перед production (migration 015)

Полное описание диагностики и обоснования — `docs/database/TRAINER_AUTH_PRODUCTION_CHECK.md`,
`supabase/diagnostics/check_trainer_club_id_compatibility.sql`. Ничего не
применялось к production в рамках этой задачи — только создание и
локальное тестирование новой миграции.

- Пользователь выполнил production-диагностику `trainers.club_id`/
  `clubs.club_short_name` в реальном проекте JCL_Gruppen — автоматический
  итог PASS: типы `text`/`text` совместимы, NOT NULL, без NULL/пустых/
  пробельных значений, без orphaned/дублирующихся `club_id`, без дублей
  `club_short_name` (ни точных, ни после `lower(trim(...))`), без FK
  `trainers.club_id → clubs.club_id`, без UNIQUE-ограничения на
  `club_short_name`.
- Финальный review сопоставил миграции 011–014 с фактической схемой:
  ни одна не изменяет структуру `public.trainers`/`public.clubs` (только
  `SELECT`), применимы последовательно без конфликтов.
- Найден реальный (не гипотетический) риск: `resolve_trainer_login_email`/
  `resolve_family_login_email` используют обычный (не `STRICT`) `SELECT
  ... INTO` по `club_short_name` — при дубликате Postgres молча взял бы
  значение из произвольной строки, не бросил бы ошибку. Фактическое
  отсутствие дублей сегодня не гарантирует их отсутствие в будущем.
- Создана и локально протестирована (`db reset` + прямые SQL-тесты в
  контейнере) `supabase/migrations/20260720120015_clubs_club_short_name_unique.sql`:
  `CHECK (btrim(club_short_name) <> '')` + `UNIQUE INDEX` на
  `lower(btrim(club_short_name))`. Оба ограничения подтверждены рабочими
  (дубликат другого регистра и пустое значение отклоняются с понятной
  ошибкой Postgres, откат без изменения данных), идемпотентны (повторное
  применение — no-op), не меняют поведение `resolve_*_login_email`
  (проверено — обе функции возвращают прежний результат после миграции).
  Миграции 011–014 не редактировались задним числом.
- Отсутствие FK `trainers.club_id → clubs.club_id` признано пред
  существующим свойством чужой таблицы `trainers` (JCL_Gruppen), не
  блокером Trainer Auth — миграция 011 сознательно использует триггеры
  вместо FK по этой же причине; добавление такого FK не входит в объём
  Trainer Auth и не рекомендовано делать в одностороннем порядке.
- Rate limiting для `resolve_trainer_login_email` классифицирован как

- **Migration 015 к production не применялась** — только создана и
  проверена локально, ожидает решения владельца.
