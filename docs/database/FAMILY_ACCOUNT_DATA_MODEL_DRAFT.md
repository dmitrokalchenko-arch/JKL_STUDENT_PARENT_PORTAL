# Черновик модели данных семейного аккаунта

Это **только концептуальная модель**. SQL, миграции и реальные структуры не
создаются. Документ сопоставляет предлагаемые новые сущности с уже
существующей таблицей `students` из `JCL_Gruppen` (см.
`docs/database/EXISTING_DATABASE_AUDIT.md`) и не предполагает создание
второй таблицы студентов.

Полное архитектурное описание — в
`docs/architecture/FAMILY_ACCOUNT_CONCEPT.md`.

---

## Соответствие с существующей таблицей `students`

Подтверждено аудитом (`EXISTING_DATABASE_AUDIT.md`, разделы 4–5):
`students` уже содержит `id`, `club_id`, `vorname`, `nachname`,
`geburtsdatum`, `foto_url`, `kyu_grad`, `guertelfarbe`, `sport_id`,
`gruppe_id`, `aktiv`, `vertrag_status` и другие поля клубного
администрирования. Ни один из документов ниже не предлагает копировать или
дублировать эту таблицу — все новые сущности **ссылаются** на
`students.id` (или на легаси `student_id`, где это уместно), не повторяя её
поля.

---

## 1. `family_accounts` — семейный аккаунт

**Назначение:** единая точка входа семьи, независимая от количества
привязанных детей.

**Утверждено:** аккаунт создаётся сотрудником клуба (семья не может
зарегистрироваться самостоятельно).

**Основные поля (концептуально, без типов):**
- `club_id` — принадлежность клубу (multi-tenant, как и везде в
  `JCL_Gruppen`);
- `family_nickname` — уникальный ник семьи, используется для входа
  (утверждено, см. `FAMILY_ACCOUNT_CONCEPT.md`, раздел 15, пункт 2);
- `recovery_email` — email, используется **только для восстановления
  пароля**, не для входа (утверждено, пункт 3);
- password/auth reference — **только концептуально**: сама модель не
  описывает, как именно хранится пароль/секрет аутентификации. Пароль в
  открытом виде **не хранится ни при каких условиях** — при реализации
  используется хеширование (аналогично уже применяемому в `JCL_Gruppen`
  подходу `pin_hash`/`pin_salt` для тренеров, см.
  `EXISTING_DATABASE_AUDIT.md`, раздел 7) либо механизм Supabase Auth;
  конкретный механизм — вопрос технического стека, не архитектуры;
- `display_name` — отображаемое имя семьи в интерфейсе;
- `status` — активен/заблокирован/ожидает подтверждения;
- `created_at`, `updated_at`.

**Связь с существующими таблицами:** самостоятельная новая сущность,
привязана к `club_id` из `clubs`. Не пересекается со `students` напрямую —
связь идёт через `family_students` (см. ниже).

**Риски:** `family_nickname` должен быть уникален как минимум в пределах
`club_id` (или глобально — уточняется на этапе технического
проектирования); необходимо предусмотреть, что смена `recovery_email`
семьёй самостоятельно (без пароля) не должна быть возможна без
дополнительной проверки.

**Открытые вопросы:** закрыты (см. `FAMILY_ACCOUNT_CONCEPT.md`, раздел 15,
пункты 1–4). Технические детали конкретного механизма хеширования/Auth —
вопрос следующего этапа (выбор стека).

**RLS:** необходима — доступ к записи `family_accounts` и ко всем связанным
данным должен быть ограничен владельцем аккаунта. Политики не создаются на
этом этапе.

## 2. `family_students` — связь семьи с учеником

**Назначение:** связывает `family_accounts` с существующей записью в
`students`, не копируя данные ученика.

**Обновлено 2026-09-24 (продуктовое решение, см. `memory/BUSINESS_RULES.md`
правило 24, `FAMILY_ACCOUNT_CONCEPT.md` раздел 15 пункт 7, migration
`20260924100069`):** один ученик может быть связан максимум с **одной
активной** семейной записью одновременно (прежнее "максимум с двумя,
например при раздельно проживающих родителях с разными аккаунтами" —
отменено; оба родителя используют один общий Familienkonto). Связь всегда
подтверждается клубом (см. `family_link_requests` ниже) — семья не может
создать её самостоятельно. Удаление связи **не удаляет** запись в
`students` — удаляется только строка `family_students`.

**Основные поля:**
- `family_account_id` — ссылка на `family_accounts`;
- `student_id` — ссылка на существующую запись `students.id`
  (`JCL_Gruppen`);
- relationship status — например, активна/приостановлена/архивна;
- `is_primary` — является ли это основной семьёй для ребёнка (изначально
  введено для сценария с двумя семьями на одного ребёнка; с 2026-09-24 этот
  сценарий не допускается — поле сохранено, но при максимум одной активной
  семье у ребёнка фактически всегда `true`);
- `linked_at` — дата установления связи;
- `linked_by` — кто подтвердил связь (сотрудник клуба);
- status — статус самой связи (не путать с relationship status выше — если
  оба нужны, различие нужно явно определить при проектировании).

**Важно:** договор и платежи **не хранятся в этой таблице** — они относятся
к конкретному ребёнку через `family_contracts`/`family_payments` (см. ниже),
а не к паре «семья↔ребёнок».

**Связь с существующими таблицами:** `student_id` → `students.id`
напрямую. Это единственная точка, где новая модель «касается» основной
таблицы, и только через ссылку, не через копирование полей.

**Риски:** сняты 2026-09-24 — сценарий с двумя активными семьями на одного
ребёнка (и связанный с ним вопрос об одновременных изменениях `is_primary`)
больше не допускается на уровне продукта и базы данных.

**Открытые вопросы:** закрыты (см. `FAMILY_ACCOUNT_CONCEPT.md`, раздел 15,
пункт 7 — обновлено 2026-09-24).

**RLS:** необходима — семья должна видеть только свои `family_students`
записи и через них — только своих детей в `students`.

## 3. `family_guardians` — родители/опекуны внутри аккаунта

**Назначение:** хранит данные родителей и опекунов внутри одного
семейного аккаунта.

**Основные поля:**
- `family_account_id`;
- имя;
- тип связи: `parent` / `guardian` / `other`;
- контактные данные;
- основной контакт (флаг);
- статус.

**Важное пояснение (обязательно к учёту при проектировании):** на первом
этапе один семейный логин используется несколькими членами семьи — то есть
**`family_guardians` не являются отдельными логинами**. Это просто список
людей, связанных с аккаунтом (для отображения в разделе «Моя семья», для
контактной информации, для будущей отчётности), а не отдельные учётные
записи с собственным паролем. Отдельная авторизация по опекуну — не входит
в первую версию (см. `FAMILY_ACCOUNT_CONCEPT.md`, раздел 14).

**Связь с существующими таблицами:** нет прямой связи со `students`;
связана только с `family_accounts`.

**Риски:** если в будущем потребуется давать разным опекунам разные права
(например, только один опекун может видеть платежи), текущая модель
«один логин на всех» этого не поддерживает — потребуется отдельное решение
позже.

**Утверждено:** добавление нового guardian отправляется как запрос и
требует подтверждения клубом (через `family_link_requests`, см. ниже) —
так же, как и привязка ребёнка. Несколько guardians продолжают
использовать один общий семейный вход — это не меняется добавлением
нового guardian.

**Открытые вопросы:** закрыты (см. `FAMILY_ACCOUNT_CONCEPT.md`, раздел 15,
пункт 6).

**RLS:** RLS применяется на уровне `family_account_id`, не на уровне
отдельного guardian (поскольку логин общий).

## 4. `family_link_requests` — запрос на привязку

**Назначение:** запрос семьи на привязку ребёнка (или добавление
родителя/опекуна), ожидающий подтверждения клубом.

**Утверждено:** оба типа запроса (привязка ребёнка и добавление
родителя/опекуна) обязательны — ни одно из этих действий не выполняется
семьёй самостоятельно и мгновенно (см. `FAMILY_ACCOUNT_CONCEPT.md`,
раздел 15, пункты 5–6).

**Основные поля:**
- `family_account_id`;
- `requested_student_id` (если запрос на привязку существующего ученика);
- `request_type` — например, «привязать ребёнка» / «добавить опекуна»;
- status — ожидает/подтверждено/отклонено;
- `requested_at`;
- `reviewed_at`;
- `reviewed_by` — сотрудник клуба, подтвердивший или отклонивший запрос.

**Связь с существующими таблицами:** `requested_student_id` → `students.id`
(если применимо).

**Риски:** без этой таблицы привязка ребёнка происходила бы мгновенно и
без проверки клубом, что противоречит правилу «добавление ребёнка
самостоятельно не выполняется без проверки клубом» (`memory/UI_RULES.md`).

**Открытые вопросы:** как именно подтверждается привязка ребёнка и
добавление опекуна (вопросы №5–6 в концепции).

**RLS:** необходима — запрос должен быть виден только своей семье и
персоналу клуба с соответствующими правами.

## 5. `family_contracts` — договор ребёнка

**Назначение:** полноценный договор (в отличие от `students.vertrag_status`,
который является лишь флагом `'OK'/'BEENDET'` без дат и истории — см.
`EXISTING_DATABASE_AUDIT.md`, раздел 5.1).

**Важно:** `students.vertrag_status` **не используется как замена**
договору — это разные уровни детализации. `family_contracts` должен
покрывать даты начала/окончания, тип продления (авто/ручное), статус.

**Утверждено (закрывает прежний открытый вопрос):** каждый договор
относится к **конкретному `student_id`**, а не к семье в целом. Договор
также связан с `family_account_id` (через какой аккаунт договор был
оформлен/виден) и с `club_id`. У разных детей одной семьи могут быть
**разные** тарифы, даты начала договора, сроки оплаты и условия договора —
это явно допускается моделью (см. `FAMILY_ACCOUNT_CONCEPT.md`, раздел 15,
пункты 11–12).

**Основные поля (концептуально):**
- `student_id` — ссылка на конкретного ребёнка (`students.id`);
- `family_account_id` — через какой семейный аккаунт оформлен/виден
  договор (с учётом того, что ребёнок может быть связан максимум с двумя
  аккаунтами — см. `family_students`);
- `club_id`;
- дата начала, дата окончания;
- тип продления — автоматическое / ручное;
- тариф;
- статус — **вычисляется по датам и условиям, где это возможно** (активен /
  истёк / скоро истекает), а не хранится отдельным изменяемым полем (см.
  общее правило «вычислять, а не хранить» в разделе «Что не нужно хранить»
  ниже и в `EXISTING_DATABASE_AUDIT.md`, раздел 11, категория E).

**Связь с существующими таблицами:** ссылается на `students.id` напрямую;
не связан с `clubs.contract_*` (SaaS-уровень клуба — не подходит, см.
критическую находку аудита).

**Риски:** если не разделить «договор клуба с платформой» и «договор
ребёнка с клубом» на уровне терминологии в UI и коде — велика вероятность
путаницы (это уже отмечено в `EXISTING_DATABASE_AUDIT.md`, Раздел 12,
пункт 3).

**Открытые вопросы:** закрыты (см. `FAMILY_ACCOUNT_CONCEPT.md`, раздел 15,
пункты 11–12).

**RLS:** необходима — доступ к договору ограничивается семьями, реально
связанными с этим `student_id` (через `family_students`), и тренерами —
только через `trainer_student_finance_summary` (см. ниже), без прямого
доступа к таблице.

## 6. `family_payments` — платежи за обучение ребёнка

**Назначение:** платежи за обучение конкретного ребёнка. Отдельно от
`club_payments` (SaaS-биллинг клуба перед платформой JCL) — это принципиально
разные уровни данных, подтверждено пользователем (см.
`FAMILY_ACCOUNT_CONCEPT.md`, раздел 15, пункт 12 и общее правило о
недопустимости путаницы).

**Утверждено:** относится к конкретному договору (`family_contracts`) и,
через него, к конкретному ребёнку (`student_id`) — не к семье как таковой
(согласуется с тем, что договор привязан к ребёнку, пункт 11 в концепции).

**Основные поля:**
- связь с договором (`family_contracts`) — и через него с `student_id`;
- период, за который произведена оплата;
- сумма;
- дата платежа;
- рабочий статус (например, оплачено/просрочено/ожидает);
- безопасное описание способа оплаты — **без хранения данных банковской
  карты** (см. ниже, «Что не нужно хранить»); конкретный формат такого
  описания и то, ссылается ли оно на внешнего провайдера (Stripe и т.п.)
  или на другой механизм, — вопрос следующего этапа (выбор технического
  стека), не архитектурное решение.

**Связь с существующими таблицами:** не связана напрямую со `students`
или `club_payments` — параллельная, отдельная сущность, доступная только
через `family_contracts` → `student_id`.

**Риски:** совпадение слова «payment» с `club_payments` может привести к
случайному переиспользованию не той таблицы — нужно явно разносить
терминологию в UI и в названиях.

**Открытые вопросы:** принципиально закрыты — платежи привязаны к ребёнку
через договор, банковские данные не хранятся никогда. Остаётся открытым
только технический выбор конкретного провайдера/формата хранения ссылки на
способ оплаты (не архитектурный вопрос).

**RLS:** необходима, включая ограничение видимости чувствительных полей от
тренерского доступа (см. `memory/BUSINESS_RULES.md`, правило 11) — тренер
не должен иметь прямого доступа к `family_payments`, только к вычисляемому
`trainer_student_finance_summary` (см. ниже).

## 7. `trainer_student_finance_summary` — вычисляемое представление для тренера

**Назначение:** дать тренеру доступ ровно к тому финансовому объёму
данных, который утверждён пользователем (см.
`FAMILY_ACCOUNT_CONCEPT.md`, раздел 15, пункты 8–10), не открывая прямой
доступ к `family_contracts`/`family_payments`.

**Это представление или вычисляемый запрос, а не хранимая таблица** — оно
агрегирует данные из `family_contracts` и `family_payments` на лету.
View/SQL не создаются на этом этапе — фиксируется только концепция.

**Утверждённый состав полей (только это, не больше):**
- `contract_status` — статус договора (вычисляется по датам, см.
  `family_contracts`);
- `paid_until` — дата, до которой оплачено;
- `has_debt` — есть ли задолженность (булево или производное значение);
- `next_payment_due` — следующий срок оплаты.

**Явно исключено из представления:** банковские реквизиты, платёжные
токены, любые чувствительные данные способа оплаты, сумма и история
отдельных платежей (эти поля остаются только в `family_payments`, видны
семье, но не тренеру).

**Доступ:** только чтение для тренера. Тренер не может через это
представление (или как-либо иначе) изменять платежи или финансовые
операции (см. `FAMILY_ACCOUNT_CONCEPT.md`, раздел 15, пункт 10).

**RLS:** представление должно быть построено так, чтобы тренер видел
только тех учеников, которые ему доступны по правилам клуба (см. открытый
технический вопрос в разделе 10 концепции про алгоритм отбора учеников).

## Что не нужно хранить

Явное намерение — не повторять антипаттерны, уже найденные в
`JCL_Gruppen` (см. `EXISTING_DATABASE_AUDIT.md`, разделы 5.1 и 11–12):

- **Вычисляемый возраст** — брать только из `geburtsdatum`, никогда не
  сохранять отдельным полем повторно (в `JCL_Gruppen` найден именно такой
  антипаттерн в поле `students.alter` — не повторять).
- **Итоговый текущий рейтинг без журнала начислений** — если понадобится
  «рейтинг», хранить журнал событий (кто, когда, за что начислено), а не
  один изменяемый счётчик.
- **Дублированный профиль ребёнка** — Family Portal не создаёт вторую
  версию данных ученика; всегда ссылка на `students.id` через
  `family_students`.
- **Копию посещаемости** — использовать существующую `attendance` напрямую,
  не копировать записи в новую структуру.
- **Копию групп** — использовать существующую `groups` напрямую.
- **Копию тренеров** — использовать существующую `trainers` напрямую.
- **Чувствительные данные банковской карты** — не хранить номера карт, CVV
  и подобные данные в собственной базе ни при каких условиях; при
  необходимости хранить только ссылку/токен внешнего платёжного провайдера.

## Общее по RLS

Все шесть хранимых сущностей (`family_accounts`, `family_students`,
`family_guardians`, `family_link_requests`, `family_contracts`,
`family_payments`) плюс вычисляемое представление
`trainer_student_finance_summary` требуют RLS-политик, привязанных к
`family_account_id` (для семейного доступа) и к `club_id` (для тренерского
и будущего административного доступа). Ни одна политика не создаётся на
этом этапе — согласно `memory/BUSINESS_RULES.md`, правило 19, RLS
проектируется отдельно и требует согласования.

Все открытые вопросы, зафиксированные в предыдущей версии этого документа,
