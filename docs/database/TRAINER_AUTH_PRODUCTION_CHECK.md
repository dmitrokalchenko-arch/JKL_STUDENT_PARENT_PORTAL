# Trainer Auth — проверка production-схемы перед применением migration 011

Эта инструкция не требует знаний SQL — только скопировать, вставить и
прислать результат. Файл, о котором идёт речь:
[`supabase/diagnostics/check_trainer_club_id_compatibility.sql`](../../supabase/diagnostics/check_trainer_club_id_compatibility.sql).

**Правило, которое нельзя нарушать: `migration 011`
(`supabase/migrations/20260720120011_create_trainer_accounts.sql`) нельзя
применять к production JCL_Gruppen, пока по всем 16 пунктам ниже не
получен результат PASS.** Если хотя бы один пункт — BLOCKER, миграция
может создать триггеры, которые либо всегда отклоняют вставку (ложные
несовпадения типов), либо (реже) пропускают то, что должны были отклонить.

## 1. Где выполнить

1. [supabase.com/dashboard](https://supabase.com/dashboard) → войти.
2. Открыть проект **JCL_Gruppen** (тот, что обслуживает текущую клубную
   систему).
3. Левое меню → **SQL Editor** → **New query**.

## 2. Как убедиться, что выбран правильный проект

Перед выполнением проверьте **название проекта в верхней части
Dashboard** (рядом с логотипом Supabase) — оно должно точно совпадать с
JCL_Gruppen. Если в вашем аккаунте несколько проектов (например, есть
тестовый/staging), URL в адресной строке браузера тоже содержит
уникальный project ref — сверьте его с тем, что использует реальное
приложение клуба. Выполнение диагностики не в том проекте даст
бессмысленный (но безопасный) результат — не разрушительно, но не
принесёт пользы.

## 3. Что этот SQL ничего не изменяет

Файл состоит **только** из запросов `SELECT` — либо к встроенным
"каталогам" Postgres (`information_schema.columns`, `pg_constraint`,
`pg_indexes`, `pg_policies`, `pg_tables` — справочники, в которых Postgres
сам хранит описание своей схемы), либо к обычным данным таблиц
`trainers`/`clubs` через `count(*)` и `SELECT DISTINCT ... LIMIT 20`. Ни
одной команды `INSERT`, `UPDATE`, `DELETE`, `CREATE`, `ALTER`, `DROP`,
`TRUNCATE`, `GRANT`, `REVOKE` в файле нет — так же, как и в уже
проверенном `check_existing_column_types.sql`. Никакие функции проекта
(RPC, SECURITY DEFINER) не вызываются. Выполнить этот файл — по риску то
же самое, что открыть "Table Editor" и посмотреть на структуру таблиц
глазами.

## 4. Как выполнить и что скопировать

1. Откройте файл `supabase/diagnostics/check_trainer_club_id_compatibility.sql`
   в текстовом редакторе, скопируйте содержимое целиком (`Ctrl+A`,
   `Ctrl+C`).
2. Вставьте в пустой запрос SQL Editor.
3. Файл состоит из **16 отдельных пронумерованных запросов** (каждый
   начинается с комментария `-- N. ...`). Чтобы увидеть результат
   **каждого** запроса отдельно (не только последнего), выделяйте и
   выполняйте (`Run` / `Ctrl+Enter`) их по одному — от `-- 1.` до `;` перед
   следующим `-- 2.`, и так далее до 16.
4. Для каждого из 16 запросов скопируйте результат (выделить таблицу
   результата мышью + `Ctrl+C`, либо кнопка **Export**/копирования над
   таблицей) и пришлите, подписав номер запроса. Если результат пустой —
   тоже напишите явно «Запрос N: пусто», это не ошибка, а иногда и есть
   ожидаемый (хороший) результат.

## 5–6. Критерии PASS / BLOCKER по каждому из 16 запросов

| № | Что проверяет | PASS | BLOCKER |
|---|---|---|---|
| 1 | Существуют ли `public.trainers` и `public.clubs` | оба `true` | любое `false` — дальнейшие пункты неприменимы, миграция невозможна без структурных изменений |
| 2 | Тип/nullable/default `trainers.club_id` | строка есть, `data_type` = `text` | строк нет (колонки не существует под этим именем) ИЛИ `data_type` ≠ `text` — миграция 011 требует правки типов перед применением |
| 3 | Общее число строк `trainers` | любое число — информационный | 0 строк само по себе не блокер, но повод перепроверить пункт 2 (правильная ли база/проект) |
| 4 | Строки `trainers` с `club_id IS NULL` | `0` | `> 0` — частичный блокер: для ЭТИХ тренеров `trainer_accounts` создать нельзя, пока `club_id` не заполнен (остальных это не блокирует) |
| 5 | Число `trainers.club_id`, отсутствующих в `clubs.club_id` | `0` | `> 0` — частичный блокер (см. пункт 4); если число велико относительно пункта 3 — требует расследования перед массовым включением тренеров |
| 6 | До 20 примеров конкретных несовпадающих `club_id` | — (используется для расследования пункта 5) | — |
| 7 | Тип `clubs.club_id` | `data_type` = `text` | строк нет ИЛИ тип ≠ `text` — блокер, требует правки миграции |
| 8 | Совпадение типов `club_id` между `trainers`/`students`/`clubs` | все три строки показывают одинаковый `data_type`/`udt_name` | расхождение — блокер, триггер `enforce_trainer_accounts_club_match` может неявно приводить типы непредсказуемо |
| 9 | Дубликаты `clubs.club_id` | пусто | любая строка — серьёзный блокер: `club_id` перестаёт однозначно определять клуб (затрагивает не только Trainer Auth, но и уже существующий Family Auth) |
| 10 | Индексы по `trainers.club_id` | информационный, не влияет на PASS/BLOCKER | — (миграция 011 не требует такого индекса; фильтрация в триггере идёт по `trainers.id`, не по `club_id`) |
| 11 | FK-ограничения на `trainers`, упоминающие `club_id` | информационный | — (наличие такого FK не мешает миграции 011, только подтверждает лишнюю гарантию) |
| 12 | Ограничение уникальности/PK на `clubs.club_short_name` | желательно наличие | отсутствие — не блокер само по себе, смотрите пункт 14 (фактические данные важнее объявленного ограничения) |
| 13 | Строки `clubs` с `club_short_name IS NULL` | `0` | `> 0` — блокер для ЭТИХ конкретных клубов: вход (семейный и тренерский) не построит технический email без `club_short_name` |
| 14 | Дубликаты `clubs.club_short_name` | пусто | любая строка — **критический блокер**: ломает детерминированное построение технического email (`resolve_family_login_email`/`resolve_trainer_login_email`) для ОБОИХ существующих auth-доменов, не только тренерского |
| 15 | RLS policies на `trainers`/`clubs` | информационный | — (все функции проекта, читающие эти таблицы, — `SECURITY DEFINER`, RLS их не ограничивает независимо от результата) |
| 16 | Включён ли RLS на `trainers`/`clubs` | информационный | — (см. пункт 15) |

**Итоговое правило:** если хотя бы один пункт из {2, 5 (полностью, не частично), 7, 8, 9, 14} — BLOCKER, миграция 011 **не применяется** до отдельного пересмотра. Пункты 4/5 (частично) не блокируют миграцию целиком — они означают, что для конкретных тренеров/клубов с проблемными данными аккаунт создать нельзя, пока данные не исправлены; это не мешает применить миграцию для остальных.

## 7. Не публиковать

Результаты запросов не содержат ФИО, email, телефоны или другие
персональные данные тренеров (только `club_id`/`club_short_name` —
идентификаторы клуба, типы колонок, количества, имена ограничений и
индексов). Если сама по себе видимость `club_id`/`club_short_name`
считается чувствительной информацией по политике владельца — можно
прислать только количества (пункты 3, 4, 5, 9, 13, 14), не сами значения
из пункта 6. Ни при каких условиях не публикуйте `service_role`/`anon`
ключи, JWT, пароли или строки подключения к базе — этот диагностический
файл их не запрашивает и они не должны появляться в переписке.

## 8. Главное правило ещё раз

**Migration 011 не применяется к production JCL_Gruppen, пока результаты
всех 16 пунктов не получены и не показывают PASS (с учётом уточнений
пунктов 4/5 выше).** До этого момента статус — `BLOCKED FOR PRODUCTION`
независимо от готовности кода и локальных тестов.
