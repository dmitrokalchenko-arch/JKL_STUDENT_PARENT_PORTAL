# Trainer Auth — rate limiting: анализ и production-чеклист

Закрывает Major-замечание #5 code review Trainer Auth. Вариант **A** —
platform-level ограничения достаточны для `signInWithPassword`; для
`resolve_trainer_login_email` защиты rate-limit НЕТ (см. исправление ниже),
но она не требуется для текущего pilot-объёма — обоснование см. в разделе
«Уточнение» (добавлено на этапе финальной production-проверки, исправляет
ошибочный вывод первой версии этого документа).

## ⚠️ Исправление (production-проверка, повторный анализ)

Первая версия этого документа утверждала, что `sign_in_sign_ups` защищает
**оба** запроса flow входа тренера, включая `resolve_trainer_login_email`.
**Это было неверно** и не проверялось по официальной документации на
момент первой версии. Проверено повторно через
[supabase.com/docs/guides/auth/rate-limits](https://supabase.com/docs/guides/auth/rate-limits):
rate limits Supabase Auth (`[auth.rate_limit]`, включая `sign_in_sign_ups`)
применяются **только** к эндпоинтам `/auth/v1/*` (`/auth/v1/signup`,
`/auth/v1/recover`, `/auth/v1/otp`, `/auth/v1/verify`, `/auth/v1/token`,
`/auth/v1/factors/*`) — нигде в официальной документации не упоминаются
эндпоинты `/rest/v1/rpc/*` (PostgREST RPC, к которым относится
`resolve_trainer_login_email`). Это два физически разных сервиса в стеке
Supabase (GoTrue для Auth, PostgREST для REST/RPC) с независимыми
ограничениями. Дополнительно подтверждено (GitHub-обсуждения
supabase/supabase, официально признанный пробел): PostgREST **не имеет
встроенного rate limiting** — команда Supabase прямо признаёт, что это
должно решаться на уровне gateway (Kong), но управляемые пользователем
контролы для этого не выставлены.

**Исправленный вывод:** `sign_in_sign_ups` защищает только
`signInWithPassword` (шаг 2 ниже). `resolve_trainer_login_email` (шаг 1)
технически не ограничен по частоте вызова ничем в стеке Supabase, кроме
общей инфраструктурной защиты hosted-платформы (Kong/CDN — не
настраиваема, не специфична для этого RPC, не то же самое, что
целевой rate limit).

## Анализ

Два разных запроса в flow входа тренера, с разной поверхностью риска:

1. **`resolve_trainer_login_email`** — обычный PostgREST RPC
   (`/rest/v1/rpc/resolve_trainer_login_email`), доступен `anon`, строит
   email детерминированно, без проверки существования аккаунта
   (анти-enumeration — см. migration 012, не меняется). **Rate limit
   Supabase Auth на него не действует (см. исправление выше).**

   Тем не менее ограничение частоты вызова этого конкретного RPC
   **не критично для анти-enumeration** по отдельной причине: сам алгоритм
   построения email открыт (виден в исходном коде проекта —
   `trainer_<club_short_name>_<hex(login_name)>@internal.jkl`), значит
   любой, кто знает алгоритм, может вычислить тот же email **локально, без
   единого запроса к серверу**. RPC не даёт атакующему ничего для
   enumeration, чего тот не мог бы получить и так.

   Отдельно от анти-enumeration — вопрос **нагрузки**: функция делает один
   `SELECT club_id FROM public.clubs WHERE club_short_name = ... AND active
   = true` (точечная выборка по одному условию) плюс дешёвые строковые
   операции (`regexp_replace`, `convert_to`, `encode`) — не полное
   сканирование таблиц, не рекурсия, не тяжёлые джойны. При типичном для
   пилотного масштаба числе клубов и отсутствии внешнего flood-трафика
   риск заметной нагрузки от повторных вызовов **низкий**, но не нулевой —
   при массовом автоматизированном переборе (тысячи запросов/сек) это
   создаст реальную нагрузку на Postgres, т.к. ничего в стеке сейчас это
   физически не останавливает раньше уровня самой БД.

2. **`signInWithPassword`** (вызывается после resolve, с полученным email)
   — это уже настоящий auth-endpoint (`/auth/v1/token?grant_type=password`).
   Здесь единственная реальная точка атаки — перебор пароля. Она уже
   покрыта встроенным лимитом Supabase Auth (см. ниже), одинаково для
   семейного и тренерского входа — они используют один и тот же
   auth-сервер (GoTrue), лимит применяется по IP, не различает роль/таблицу.

**Вывод (исправленный):** дополнительная SQL-таблица попыток входа —
по-прежнему не обоснована прямо сейчас (не по указанию пользователя —
требует отдельной команды на реализацию, а не автоматического решения
здесь). Но заявление «`resolve_trainer_login_email` уже защищена
platform-level лимитом» было ошибочным и снято. Честная текущая позиция:
для RPC защиты по частоте вызова нет; для текущего pilot-масштаба это
приемлемый, осознанный gap (низкая ожидаемая нагрузка, анти-enumeration
не зависит от rate limit), а не «закрытый» вопрос — см. чеклист ниже.

## Фактическая текущая конфигурация (локальный `supabase/config.toml`)

```toml
[auth.rate_limit]
sign_in_sign_ups = 30   # запросов входа/регистрации за 5 минут на IP
token_refresh = 150
token_verifications = 30
```

`[auth.captcha]` — присутствует в конфиге, но закомментирован (не включён).

Отдельного `[api.rate_limit]` для PostgREST RPC-эндпоинтов (в т.ч.
`resolve_trainer_login_email`) в `config.toml` нет — такой секции в
Supabase CLI-конфигурации не существует в принципе на момент этой проверки.
**Подтверждено официальной документацией** (см. раздел «Исправление»
выше) — это не пробел в конкретно нашей конфигурации, это общее свойство
PostgREST в стеке Supabase на данный момент.

## Production-чеклист (для владельца проекта, не выполняется мной)

- [ ] Подтвердить в Supabase Dashboard реального проекта (не в локальном
      `config.toml` — managed-хостинг может иметь свои platform-default
      значения, отличные от локальных), что `sign_in_sign_ups` rate limit
      включён и его значение приемлемо для ожидаемого числа тренеров/семей.
      **Действует только на `signInWithPassword`, не на
      `resolve_trainer_login_email`/`resolve_family_login_email`.**
- [ ] Рассмотреть включение `[auth.captcha]` (hCaptcha/Turnstile) на формах
      входа (семейной и тренерской) при выходе в production — особенно если
      число пользователей вырастет настолько, что 30 попыток/5 мин на IP
      станет узким местом для легитимных пользователей за NAT (офис клуба).
- [ ] Если в будущем `resolve_trainer_login_email`/`resolve_family_login_email`
      будут расширены и начнут возвращать что-то, кроме детерминированного
      email (например, признак активности) — это изменит анти-enumeration
      модель и потребует пересмотра этого анализа заново.
- [ ] **Новое:** осознанно принять или закрыть gap отсутствия rate limit на
      `resolve_trainer_login_email`/`resolve_family_login_email` как PostgREST
      RPC. Для текущего pilot-масштаба одного клуба реализация не требуется
      прямо сейчас (см. «Исправление» — риск нагрузки низкий, анти-enumeration
      не зависит от rate limit). Если нагрузка/число клубов вырастет, или
      появится сигнал реальных злоупотреблений, минимальный
      production-вариант (не реализуется в рамках этой задачи, требует
      отдельной команды): обернуть resolve-вызов в Edge Function перед
      PostgREST и подключить внешний rate limiter (например, Upstash Redis —
      официально упоминаемый Supabase workaround) ИЛИ поставить перед
      Supabase внешний gateway (Cloudflare и т.п.). SQL-таблица попыток входа
      — сознательно не выбрана как первый вариант (усложняет схему больше,
      чем Edge Function-обёртка, ради того же результата).

## Не входит в объём этого документа

Полноценный API gateway rate limiting (Kong-level, для self-hosted
развёртываний) — не проверялся, т.к. текущий проект использует managed
Supabase; при переходе на self-hosted это нужно проверить отдельно.
