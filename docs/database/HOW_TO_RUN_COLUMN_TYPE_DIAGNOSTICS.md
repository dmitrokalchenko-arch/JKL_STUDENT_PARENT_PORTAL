# Как выполнить диагностику типов в Supabase Dashboard (шаг 0 этапа 2.2)

Эта инструкция не требует знаний SQL или Supabase — только скопировать и
вставить. Речь идёт о файле
[`supabase/diagnostics/check_existing_column_types.sql`](../../supabase/diagnostics/check_existing_column_types.sql)
в этом проекте.

## Почему это безопасно

Файл содержит **только** запросы `SELECT` к служебным «каталогам» Postgres
(`information_schema.columns`, `pg_tables`, `pg_policies`) — это встроенные
списки-справочники, в которых Postgres сам хранит описание своих таблиц:
названия колонок, их типы, что является первичным ключом и т.д. Такой
запрос **читает описание базы, а не сами данные** — он не может ничего
создать, изменить или удалить, даже теоретически. Ни в одной строке файла
нет команд `INSERT`, `UPDATE`, `DELETE`, `CREATE`, `ALTER`, `DROP` — это
проверено отдельно (поиском по файлу). Выполнить его — то же самое по риску,
что открыть страницу «Table Editor» в Dashboard и посмотреть список колонок
глазами, только результат сразу в удобной таблице.

## 1. Где открыть SQL Editor

1. Откройте [supabase.com/dashboard](https://supabase.com/dashboard) и
   войдите в свой аккаунт.
2. На странице со списком проектов откройте проект **JCL_Gruppen** (тот, на
   котором работает текущая клубная система).
3. В левом вертикальном меню найдите иконку **SQL Editor** (обычно похожа на
   `</>` или подписана "SQL Editor") и нажмите на неё.

## 2. Как создать новый SQL-запрос

1. В SQL Editor нажмите кнопку **New query** (обычно в правом верхнем углу
   или в верхней панели вкладок).
2. Откроется пустое окно редактора с курсором — сюда будем вставлять текст.

## 3. Как скопировать и выполнить диагностический скрипт

1. В этом проекте откройте файл
   `supabase/diagnostics/check_existing_column_types.sql` в любом текстовом
   редакторе (например, в том же VS Code, где открыт проект).
2. Выделите **всё содержимое файла целиком** (можно нажать `Ctrl+A`, затем
   `Ctrl+C` для копирования).
3. Вернитесь в окно SQL Editor в Supabase Dashboard, откройте в нём пустой
   запрос из шага 2 и вставьте скопированный текст (`Ctrl+V`).
4. Нажмите кнопку **Run** (или сочетание клавиш `Ctrl+Enter` /
   `Cmd+Enter` на Mac) в правом нижнем/верхнем углу редактора.
5. Скрипт состоит из **8 отдельных запросов подряд** — Supabase SQL Editor
   выполнит их все и обычно покажет результат **последнего** запроса
   (восьмого) в основной таблице снизу. Чтобы увидеть результаты
   **каждого** из 8 запросов по отдельности, самый надёжный способ —
   выполнить их по одному:
   - Выделите мышью только текст первого запроса (от `-- 1.` до символа `;`
     в конце этого блока, не включая следующий `-- 2.`).
   - Нажмите **Run** — Supabase выполнит только выделенный текст.
   - Скопируйте результат (см. шаг 4 ниже).
   - Повторите для запросов 2, 3, 4, 5, 6, 7, 8 по очереди.
   - Так дольше, но результат каждого запроса будет виден отдельно и ничего
     не потеряется.

## 4. Какие результаты скопировать и прислать

Для **каждого** из 8 запросов, после нажатия **Run**:

1. Под редактором появится таблица с результатом.
2. В правом верхнем углу этой таблицы результатов обычно есть кнопка
   **Export** или значок копирования — либо просто выделите всю таблицу
   мышью (включая заголовки колонок) и скопируйте (`Ctrl+C`).
3. Вставьте скопированное в ответное сообщение мне, подписав, какой это
   запрос по номеру (например: «Результат запроса 1:», затем сама таблица).
4. Если у какого-то из 8 запросов результат оказался **пустым** (0 строк) —
   это тоже важный результат, напишите явно «Запрос N: пусто», не
   пропускайте.

Прислать нужно результаты **всех 8 запросов**, даже если некоторые кажутся
похожими друг на друга — они проверяют разные вещи (см. ниже).

## 5. Что именно должно быть видно в результатах

| № запроса | Что проверяет | Ожидаемые строки в результате |
|---|---|---|
| 1 | Все колонки таблиц `clubs`, `students`, `trainers` — их типы | Много строк; среди них обязательно должны быть `clubs.club_id`, `students.id`, `students.club_id`, `trainers.trainer_id`, `trainers.club_id` со своими типами (столбец `data_type`) |
| 2 | Какая колонка реально является PRIMARY KEY в каждой из трёх таблиц | По одной (иногда больше) строке на таблицу — покажет точное имя PK-колонки, даже если оно отличается от предположений в наших миграциях |
| 3 | Все обязательные (`NOT NULL`) колонки `students` | Список колонок — нужен, чтобы тестовые данные (`seed.sql`) не упали при вставке |
| 4 | Включён ли Row Level Security (RLS) на `clubs`/`students`/`trainers` уже сейчас | По одной строке на таблицу, колонка `rowsecurity` = true/false |
| 5 | Если RLS включён — какие именно правила (policies) уже действуют | Может быть пусто, если RLS выключен — это нормально |
| 6 | Существуют ли `clubs.club_short_name` и `clubs.active` под этими именами | 2 строки (если поля существуют под другими названиями — обнаружится их отсутствие) |
| 7 | Типы `students.guertelfarbe`, `students.kyu_grad`, `students.club_id` (поля пояса и клуба) | 3 строки |
| 8 | Тип `auth.users.id` (встроенная таблица пользователей Supabase Auth) | 1 строка, обычно `uuid` |

Особенно важны: **тип `data_type`/`udt_name`** для `clubs.club_id`,
`students.id`, `trainers.trainer_id` и `auth.users.id` — именно от них
зависит, нужно ли переписывать миграции (если это `bigint`/`integer`/
`text`, а не `uuid`).

## Что дальше

После того как вы пришлёте результаты всех 8 запросов, следующим шагом я:
1. сравню фактические типы с тем, что предполагают миграции;
2. при необходимости поправлю все внешние ключи и функции под реальные типы;
3. покажу diff по каждому изменению;
4. проведу повторный статический аудит уже исправленных файлов;
5. подготовлю финальный пакет для локального/staging-тестирования.

Ничего из миграций/seed/Edge Function на этом шаге не запускается и не
применяется — только чтение результатов диагностики.
