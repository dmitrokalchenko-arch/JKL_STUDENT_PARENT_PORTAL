# Снимки отката (rollback snapshots)

Папка хранит снимки состояния **RLS, policies и грантов** в production
(Supabase, project ref `whorwleydkziejjafsea`), снятые **до** изменения прав.
Это страховка: если после изменения что-то сломалось в JCL_Gruppen
(Block 1), MINI_OBI_SCOREBOARD (Block 2) или в портале (Block 3), права
возвращаются ровно к зафиксированному состоянию.

Файлы здесь — только документация. Их никто не применяет автоматически, они не
являются миграциями и не лежат в `supabase/migrations/`.

## Правило

**Снимок снимается ПЕРЕД каждым изменением policies или грантов — не раз в
неделю и не «когда-то раньше».** Откатываться нужно к состоянию непосредственно
перед изменением. Если между снимком и изменением кто-то что-то поменял, старый
снимок это изменение потеряет.

Порядок для каждого изменения:

1. Прогнать генератор снимка (SQL-пречек 2.6 из аудита Security Block 1) —
   он только читает `pg_policies`, `pg_class` и
   `information_schema.role_table_grants`, ничего не выполняет.
2. Сохранить вывод сюда новым файлом с датой.
3. Закоммитить файл до применения изменения.
4. Только после этого применять изменение.

## Формат имени

```
security_block1_rollback_YYYY-MM-DD.sql
```

Если в один день снимков несколько — добавить суффикс:
`security_block1_rollback_YYYY-MM-DD_2.sql`. В начале файла — комментарий
с датой, project ref, источником, назначением и охватом (какие таблицы вошли).

## Как применять при откате

Снимок содержит только `alter table … row level security`, `create policy` и
`grant`. Сам по себе он **ничего не удаляет и не отзывает**, поэтому откат —
это три шага в одной транзакции в SQL Editor (выполняет только владелец):

1. Сверить: какие policies и гранты появились после снимка (тот же генератор
   2.6 → сравнить с файлом).
2. `begin;`
   - `drop policy if exists "<имя>" on public.<таблица>;` — для **каждой
     новой** policy и для каждой policy из снимка, которую изменение
     пересоздало под тем же именем;
   - `revoke … on public.<таблица> from <роль>;` — для **новых** грантов,
     которых нет в снимке;
   - выполнить из файла снимка нужные строки `alter table`, `create policy`,
     `grant` (policies, которые сохранились без изменений, повторно не
     создавать — `create policy` с существующим именем завершится ошибкой).
3. Снова прогнать генератор 2.6 и сравнить вывод с файлом снимка построчно.
   Совпало — `commit;`, не совпало — `rollback;` и разбираться.

После отката проверить: вход в JCL_Gruppen (Trainer, Admin, Buchhaltung,
Super Admin), регистрацию в MINI_OBI_SCOREBOARD, вход тренера и семьи в
портал.

## Ограничения снимка

Охват зависит от генератора. У снимка `2026-09-30` охват — 15 таблиц
(список — в комментарии в начале файла); **не входят** гранты на колонки,
гранты на функции, остальные таблицы JCL и таблицы портала. Если изменение
затрагивает что-то вне охвата — перед изменением расширить генератор и снять
снимок заново.
