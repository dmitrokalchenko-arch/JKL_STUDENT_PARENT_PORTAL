**Дополнительно подтверждённые колонки `students`, не запрошенные явно в
задании, но важные:**

`student_id` (альтернативный/легаси идентификатор), `trainer` (имя тренера
текстом прямо на записи студента, помимо `trainer_groups`), `mitglied_typ`
(`AKTIV` / `FOERDERMITGLIED` / `PROBETRAINING` / `INAKTIV` / `ARCHIV`),
`training_relevant`, `foerdermitglied_seit`, `foerdermitglied_ende`,
`buchhaltung_kommentar`, `buchhaltung_relevant`, `buchhaltung_datum`,
`vertrag_status` (`'OK'` / `'BEENDET'`), `vertrag_datum`,
`vertrag_geprueft_von`, `kommentar`, `austrittsdatum`, `austrittsgrund`,
`probetraining_status`, `probetraining_start`, `probetraining_ende`,
`wiederkehrer`, `aktuelles_gewicht`, **`alter`** (возраст).

⚠️ **Важная находка:** колонка `alter` (возраст) **хранится как значение**,
а не только вычисляется. Код содержит `student.alter = age` — вычисленный
возраст записывается обратно в объект и затем сохраняется в БД
(`archivPayload: { alter: student.alter }`, аналогично в других местах).
Это именно тот антипаттерн, которого создатели портала просили избежать
(«не хранить вычисляемый возраст», «не предлагать хранить вычисляемый
возраст»). Возраст пересчитывается из `geburtsdatum` только как fallback,
если `alter` не задан — то есть в реальных данных значение может быть
устаревшим. **Это не рекомендация повторять в новом портале, а
зафиксированный риск существующей системы.**

## 6. Связи между таблицами

Подтверждено по коду (через использованные foreign-key-подобные поля, а не
через реальные constraint'ы БД, которые не видны без Dashboard):

```
clubs (club_id) ──< students, trainers, groups, trainer_groups, attendance,
                     archiv, weight_log, club_payments, sponsors,
                     promo_settings/media/slides, club_yearly_snapshots,
                     club_monthly_stats            [club_id встречается 222 раза в app.js]

groups (gruppe_id) ──< trainer_groups (gruppe_id)
groups (gruppe_id) ──< attendance (gruppe_id)
groups (gruppe_id) ── sport_id → sports (sport_id)   [логическая, не проверена как FK constraint]

students (id / student_id) ──< attendance (student_id)
students (gruppe_id) ──?── groups (gruppe_id)         ⚠️ через строку с разделителем, не через
                                                          нормальную связь один-ко-многим/многие-ко-многим

trainers (trainer_id) ──< trainer_groups (trainer_id)

archiv — не связана FK, это независимая копия структуры students (insert
          дублирует данные, а не ссылается на students.id)
```

🔴 Все перечисленные связи подтверждены **только на уровне логики
приложения** (какие поля используются вместе в запросах). Реальные foreign
key constraints, ON DELETE правила и индексы в БД не проверялись — это
требует Supabase Dashboard.

## 7. Использование таблиц в коде

| Таблица | Основные операции | Realtime | RPC |
|---|---|---|---|
| `students` | select, insert, update (архивация переносит данные в `archiv`, а не удаляет) | 🔴 не обнаружено | 🔴 не обнаружено |
| `attendance` | select, insert, update (ручная проверка перед insert/update) | 🔴 не обнаружено | 🔴 не обнаружено |
| `groups`, `trainers`, `trainer_groups`, `sports` | select, insert, update | 🔴 не обнаружено | 🔴 не обнаружено |
| `club_payments`, `tariff_packages`, `clubs` | select, insert, update (только в разделе Super-Admin) | 🔴 не обнаружено | 🔴 не обнаружено |
| `archiv` | insert, update, select | 🔴 не обнаружено | 🔴 не обнаружено |

**Realtime-каналы (`.channel(...)`) и RPC-функции (`.rpc(...)`) не найдены ни
разу во всём `app.js`.** Всё взаимодействие идёт через прямые
select/insert/update/delete к таблицам.

**Supabase Auth не используется вообще** — ни одного вызова
`supabase.auth.*` не найдено. Авторизация тренеров реализована через
собственную PIN-логику (`pin_hash`/`pin_salt`, PBKDF2 в браузере) с прямой
сверкой по таблице `trainers`, минуя стандартный механизм Supabase Auth.
Это означает: **у студентов и родителей в существующей системе нет вообще
никакого логина** — это чисто административный инструмент для тренеров/клуба.
Это первое приложение, для которого потребуется настоящий пользовательский
логин студентов/родителей.

Storage buckets, подтверждённые по коду: `promo-transition`, `promo_slides`,
а также публичные пути `Startseite_1/*`, `Buttons/*` (статичные изображения
интерфейса, не связаны с профилями студентов).

RLS-политики: 🔴 **не обнаружены ни в коде, ни в документации проекта.**
Так как весь доступ идёт через анонимный (anon) ключ без Supabase Auth,
разграничение доступа, судя по всему, либо отсутствует на уровне БД (RLS
выключен/permissive), либо реализовано не через стандартный auth.uid().
**Это нужно проверить напрямую в Supabase Dashboard** перед тем, как
проектировать RLS для нового портала — потому что новый портал обязан
разграничивать доступ Student/Parent по ролям, а текущая база, похоже, для
этого не имеет готовой основы.

> ✅ **Уточнено в этапе 2.2** (диагностика реальной базы, 20.07.2026): RLS на
> `students` и `trainers` **включён** (`rowsecurity = true`), на `clubs` —

## 10. Недостающие данные

Итоговый список сущностей, отсутствующих в текущей системе (только оценка,
**ничего не создавалось**):

1. Модель «Родитель» и связь «родитель ↔ ребёнок» (несколько детей на
   родителя, потенциально несколько родителей на ребёнка).
2. Логин/учётные записи для студентов и родителей (сейчас логина нет вовсе —
   есть только PIN-логин тренеров).
3. Belt Techniques — список техник, обязательных для конкретного
   пояса/ступени.
4. Student Technique Progress — фактический прогресс освоения техник
   конкретным студентом (реальное состояние, не вычисляется).
5. Achievements (справочник) + факт получения достижения студентом.
6. Certificates — сертификаты/дипломы (файл, дата, тип).
7. Events + Event Participants — мероприятия клуба и участие в них.
8. Понятие «минимальный возраст допуска к экзамену» — сейчас не привязано
   ни к `belts`/`kyu_lookup`, ни к какой-либо другой таблице.
9. Family/Parent Contract — договор семьи с клубом: даты начала/окончания,
   тип продления (авто/ручное), статус.
10. Family Payments — платежи семьи клубу за обучение (принципиально
    отдельно от `club_payments`, которые про SaaS-биллинг клуба).
11. Club Messages — сообщения клуба родителям (и, возможно, читаемость
    сообщения по получателям).
12. Rating/Points ledger под понятие «рейтинговые баллы» из продуктового
    видения (в отличие от текущего вычисляемого счётчика тренировок).

Не найдено вообще, хотя упоминались в задании как гипотезы: `tournaments`,
`participants`, `matches`, `age_groups` (как отдельная таблица), `weight_groups`
(как отдельная таблица), `payments` в смысле платежей семьи. Их отсутствие
подтверждено — ни одного вызова `.from()` с такими именами во всём `app.js`
не найдено.

## 11. Рекомендации без SQL

### A. Использовать как есть
- `students` — как единый источник профиля студента для Student Portal и
  Parent Portal (без создания второй/дублирующей таблицы студентов).
- `groups`, `trainer_groups`, `sports` — для отображения тренировок.
- `attendance` — для истории посещений и статистики родителя, без создания
  отдельной таблицы-сводки.

### B. Добавить несколько колонок (обсудить необходимость и последствия)
- Возможно, в `students` стоит добавить структурированные поля вместо
  текущего текстового `vertrag_status`, но это меняет уже используемую
  тренерами админку — **требует согласования с владельцем JCL_Gruppen**, а
  не решается в одностороннем порядке со стороны нового портала.
- В `groups`/`kyu_lookup` может понадобиться явное поле «минимальный возраст
  экзамена» — сейчас нигде не хранится.

### C. Нужна новая связующая таблица
- `parent_student_links` (родитель ↔ студент, many-to-many).
- `student_technique_progress` (студент ↔ техника ↔ статус освоения).
- `event_participants` (студент ↔ мероприятие).
- `student_achievements` (студент ↔ достижение).

### D. Нужна новая самостоятельная таблица
- `belt_techniques` (список техник по поясу/ступени).
- `achievements` (справочник типов достижений).
- `certificates`.
- `events`.
- `club_messages`.
- `family_contracts` (договор семьи, отдельно от `clubs.contract_*`).
- `family_payments` (платежи семьи, отдельно от `club_payments`).
- Таблица авторизации студентов/родителей (или интеграция с Supabase Auth) —
  сейчас отсутствует полностью.

### E. Вычислять, а не хранить
- Возраст студента — только из `geburtsdatum`, никогда не хранить повторно
  (см. находку про `alter` в разделе 5.1 — это существующий антипаттерн,
  который не нужно повторять в новой системе).
- Следующий пояс — вычислять относительно текущего по справочнику ступеней.
- Статус договора (активен/истёк) — вычислять из дат начала/окончания.
- Следующий платёж и текущий оплаченный период — вычислять из истории
  платежей + условий договора.
- Статистика посещаемости для родителя — вычислять из `attendance`, не
  хранить отдельную сводную таблицу.

## 12. Риски дублирования

1. **`students.gruppe_id` как строка с разделителем** (`;`/`,`) для
   многогрупповой принадлежности — это уже существующий паттерн денормализации
   в `JCL_Gruppen`. Если новый портал будет читать те же данные напрямую,
   нужно либо использовать ту же логику разбора (без дублирования данных в
   новую структуру), либо явно согласовать с пользователем переход на
   отдельную связующую таблицу студент↔группа — но **это решение затрагивает
   основной проект JCL_Gruppen**, а не только новый портал.
2. **`archiv` дублирует всю структуру `students`** через полное копирование
   полей при архивации, а не через ссылку на `students.id` + флаг. Это
   осознанный выбор существующей системы — при проектировании нового портала
   не стоит копировать этот паттерн для новых сущностей (достижения,
   сертификаты и т.д.), где вместо копирования данных можно использовать
   мягкое удаление (soft delete) через флаг.
3. **`clubs.contract_*` / `club_payments` vs будущие `family_contracts` /
   `family_payments`** — критически важно не путать эти два уровня
   (платформа↔клуб и клуб↔семья). Совпадение слов «contract»/«payment» в
   названии — не повод переиспользовать таблицу.
4. **Рейтинг как вычисляемое значение** (`calculatedRating`,
   `trainingsgesamt`) уже существует в `JCL_Gruppen` — при проектировании
   «рейтинговых баллов» для нового портала стоит явно решить, это тот же
   механизм (тогда переиспользуем `attendance`) или принципиально другая
   бизнес-логика (тогда нужен отдельный журнал начислений, но не два
   параллельных «рейтинга» без объяснения разницы пользователю).
