# Threat Model — единая авторизация тренеров (JCL_Gruppen ↔ Trainer Area)

Статус: локальная реализация протестирована (`.local-supabase-test`), production не затронут.
Область: `manage-trainer-account` Edge Function, RPC `trainer_has_active_account`/`trainer_has_any_account`/
`resolve_trainer_login_email`/`rename_trainer_login`/`log_trainer_account_operation`, ветвление
логина в JCL_Gruppen (`app.js`), таблицы `trainer_accounts`/`trainer_account_audit_log`.

## 1. Активы

| Актив | Чувствительность | Где хранится |
|---|---|---|
| `auth.users` (email, password hash, session) | Высокая | Supabase Auth (GoTrue), управляется только через Admin API |
| `trainer_accounts` (login_name, club_id, is_active, привязка к auth_user_id) | Высокая | `public.trainer_accounts`, RLS enabled без policy — доступ только через SECURITY DEFINER RPC/service_role |
| `trainers` (чужая таблица JCL_Gruppen: pin_hash, pin_salt, rolle, email) | Высокая | `public.trainers`, читается манипулятором как внешняя система |
| Пароли (portal password, legacy PIN) | Критическая | Portal password — только в GoTrue (bcrypt); legacy PIN — `trainers.pin_hash`/`pin_salt` (PBKDF2, клиентский расчёт) |
| JWT (access/refresh token) | Высокая | Только в браузере администратора/тренера, никогда на сервере вне запроса |
| `club_id` (принадлежность к клубу) | Средняя | Определяет границу изоляции между клубами — компрометация ведёт к межклубному доступу |
| Административные операции (create/update/activate/deactivate) | Высокая | Выполняются только `manage-trainer-account`, по JWT + серверной проверке роли |
| Аудит-лог (`trainer_account_audit_log`) | Средняя | Кто/кого/когда/какая операция — без секретов; используется для расследования инцидентов |

## 2. Участники

| Участник | Возможности |
|---|---|
| Владелец системы | Полный доступ через Supabase Dashboard/Admin API, создаёт первого администратора |
| Администратор клуба | `trainers.rolle='Admin'` + активный `trainer_accounts`; управляет доступом тренеров СВОЕГО клуба |
| Обычный тренер | Валидная сессия, но не может вызывать `manage-trainer-account` (403) |
| Тренер другого клуба (в т.ч. администратор другого клуба) | Валидная сессия в чужом клубе; должен получать 403 при попытке доступа к чужому клубу |
| Немигрированный PIN-пользователь | Нет `trainer_accounts`, вход только по legacy PIN, не участвует в JWT-модели вообще |
| Анонимный пользователь | Может вызывать только `trainer_has_active_account`/`trainer_has_any_account`/`resolve_trainer_login_email` (anon grant, без раскрытия email/логина) |
| Злоумышленник с доступом к браузеру | Может читать/менять DOM, JS-переменные, localStorage — но НЕ service_role/секреты (их там нет) |
| Злоумышленник с украденным JWT | Действует как жертва до истечения токена (~1 час) или до явного `signOut` |

## 3. Границы доверия

```
[Браузер JCL_Gruppen]  ── НЕ доверенная зона: роль/clubId только для UI, anon key публичен
        │ Authorization: Bearer <access_token>
        ▼
[Kong / verify_jwt]     ── платформенный гейт: синтаксически/криптографически невалидный JWT отклоняется ДО кода функции
        │
        ▼
[Edge Function manage-trainer-account]  ── ЕДИНСТВЕННАЯ точка принятия решения "разрешено/запрещено"
        │ service_role (серверный секрет, никогда не покидает функцию)
        ▼
[Supabase Auth / PostgREST / RPC]  ── источники истины: auth.users, trainer_accounts, trainers
        │
        ▼
[Postgres, миграции 011-026]  ── схема, констрейнты, триггеры, RLS
```

Отдельно:
- **Production Dashboard** — вне зоны действия этой сессии, доступен только владельцу системы, не затрагивался.
- **Локальный стенд** (`.local-supabase-test`) — изолирован от production (свой Docker, свой project ref), используется только для тестов.

## 4. Угрозы

### 4.1 Подделка роли Admin во frontend
- **Сценарий:** злоумышленник правит `currentTrainer.role = 'Admin'` в консоли браузера и вызывает `submitTrainerPortalAccess()`.
- **Вероятность:** высокая (тривиально технически).
- **Влияние:** без серверной проверки — полный захват управления тренерами.
- **Защита:** Edge Function проверяет роль ТОЛЬКО через собственный fresh DB-запрос по `auth_user_id` из JWT; клиентский `role` нигде не читается сервером.
- **Остаточный риск:** нет — проверено тестом C (403).
- **Рекомендация:** без изменений.

### 4.2 Подмена `clubId`
- **Сценарий:** злоумышленник добавляет/меняет `clubId` в теле запроса.
- **Вероятность:** высокая технически (поле раньше существовало).
- **Влияние:** межклубный захват без исправления был бы критическим.
- **Защита:** `clubId` полностью удалён из payload; используется только `adminClubId`, взятый из БД по JWT.
- **Остаточный риск:** нет — проверено тестом D (403 `trainer_club_mismatch`).
- **Рекомендация:** без изменений.

### 4.3 Повторный вызов запроса (replay/double-submit)
- **Сценарий:** двойной клик/сетевой ретрай отправляет один и тот же CREATE дважды.
- **Вероятность:** средняя (обычное поведение UI без debounce).
- **Влияние:** до фикса — риск двух `trainer_accounts` на одного тренера (см. 4.9).
- **Защита:** `UNIQUE(trainer_row_id)` (migration 026) + `UNIQUE(auth_user_id)` + `UNIQUE(club_id, normalized_login_name)` + глобальная уникальность email в `auth.users`.
- **Остаточный риск:** второй запрос получает 409/500 вместо тихого дублирования — пользователю нужно повторить операцию (не автоматизировано).
- **Рекомендация:** можно добавить debounce/disable кнопки на фронте (не сделано — вне обязательного объёма, UX-улучшение).

### 4.4 Украденный JWT
- **Сценарий:** XSS/malware/логи перехватывают access_token администратора.
- **Вероятность:** зависит от общей защищённости фронтенда (XSS в JCL_Gruppen отдельно не аудировался в этой сессии).
- **Влияние:** злоумышленник действует как администратор клуба до истечения токена.
- **Защита:** ограничение по времени жизни токена (по умолчанию ~1 час), audit-лог фиксирует операции (позволяет расследовать).
- **Остаточный риск:** до истечения токена операции неотличимы от легитимных.
- **Рекомендация:** в production рассмотреть более короткий TTL access_token для этой роли и/или требовать повторную аутентификацию для чувствительных операций (не реализовано, требует отдельного решения владельца).

### 4.5 Истёкший JWT
- **Сценарий:** клиент шлёт просроченный токен.
- **Защита:** `supabaseAdmin.auth.getUser(token)` отклоняет — 401 `invalid_or_expired_token`; также перехватывается платформенным `verify_jwt` до кода функции.
- **Остаточный риск:** нет — проверено тестом F.

### 4.6 Деактивированный аккаунт с ещё живой сессией
- **Сценарий:** администратора деактивируют, у него уже есть валидный JWT.
- **Защита:** `manage-trainer-account` делает FRESH запрос `is_active` при КАЖДОМ вызове (не доверяет claims из JWT) — следующий вызов получает 403. Аналогично для Trainer Area: все бизнес-RPC обязаны использовать `private.current_active_trainer_account_id()` (архитектурное правило, migration 014), которая тоже проверяет `is_active` заново при каждом вызове.
- **Остаточный риск:** сам JWT остаётся криптографически валиден до истечения (~1 час) — `auth.getUser()` для него не откажет, но НИ ОДНА бизнес-операция после деактивации не проходит.
- **Рекомендация:** при необходимости мгновенного обнуления сессии — вызывать `supabaseAdmin.auth.admin.signOut(authUserId, 'global')` в момент деактивации (не реализовано в этой сессии, опциональное усиление, обсудить с владельцем перед production).

### 4.7 Brute force пароля
- **Сценарий:** подбор пароля портального доступа.
- **Защита:** пароль минимум 8 символов (`MIN_PASSWORD_LENGTH`), проверка выполняется через `signInWithPassword` (Supabase Auth) — сам GoTrue имеет встроенный rate-limit на попытки входа. JCL_Gruppen дополнительно имеет собственный `_checkLoginLockout`/`_recordFailedLogin` (существующий механизм, не менялся).
- **Остаточный риск:** конкретные параметры rate-limit GoTrue на production не проверялись в этой сессии (локальный стенд использует стандартные dev-настройки).
- **Рекомендация:** проверить production rate-limit настройки GoTrue перед пилотом (пункт preflight в runbook).

### 4.8 Перечисление login_name / существования тренера
- **Сценарий:** анонимный вызывающий подбирает `trainer_id`+`club_id`, наблюдая ответы `trainer_has_active_account`/`trainer_has_any_account`/`resolve_trainer_login_email`.
- **Защита:** эти RPC возвращают только boolean/детерминированный email, никогда email реального тренера, auth_user_id или login_name. anon-доступ к ним — осознанное решение, задокументированное ещё в migration 019/012: `trainers` и так публично читаема anon-ключом в существующей архитектуре JCL_Gruppen.
- **Остаточный риск:** сам факт "у trainer_id X есть/нет аккаунта" раскрывается анонимно — предсуществующий, принятый риск, не введён этой задачей.
- **Отдельно (введено в этой сессии):** ответ `manage-trainer-account` различает `trainer_not_found` (404) и `trainer_club_mismatch` (403) для АДМИНА (не анонима) — это осознанный компромисс ради соответствия явному тестовому сценарию D; администратор одного клуба может отличить "trainerId существует в другом клубе" от "не существует нигде". Раскрывается только САМ ФАКТ существования business-id, не email/пароль/принадлежность к конкретному другому клубу.
- **Рекомендация:** если анти-энумерация станет приоритетнее диагностируемости ошибок — можно объединить оба случая в единый 404, но это требует пересмотра теста D по явному запросу владельца (сознательно не сделано без такого запроса).

### 4.9 Race condition при параллельном создании
- **Сценарий:** два одновременных запроса на создание аккаунта для одного `trainer_row_id` с разными `login_name`.
- **Найдено и исправлено в этой сессии:** `UNIQUE(trainer_row_id)` (migration 026) — второй параллельный INSERT получает `unique_violation` → 409.
- **Остаточный риск:** пользователь получает ошибку и должен повторить операцию вручную — не автоматический retry.

### 4.10 Orphaned `auth.users`
- **Сценарий:** `createUser` успешен, но вставка в `trainer_accounts` падает НЕ из-за дубликата (например, кратковременная сетевая ошибка), и последующий компенсирующий `deleteUser` ТОЖЕ падает.
- **Защита:** основной путь отката (`deleteUser` при неудачной вставке) реализован и протестирован (тест I/сценарий отката в предыдущей сессии).
- **Остаточный риск:** двойной сбой (INSERT падает И delete падает) технически возможен — Postgres и GoTrue не разделяют одну транзакцию, полностью исключить нельзя без распределённой транзакции, что несоразмерно объёму задачи.
- **Рекомендация:** периодическая сверочная SQL-проверка "auth.users без соответствующей trainer_accounts, но с email вида `trainer_%@internal.jkl`" как часть planового обслуживания (шаблон — в runbook, раздел мониторинга).

### 4.11 Orphaned `trainer_accounts`
- **Сценарий:** `trainer_accounts` существует, а связанный `auth.users` удалён напрямую (в обход Edge Function).
- **Защита:** `trainer_accounts.auth_user_id` имеет `ON DELETE CASCADE` на `auth.users(id)` — удаление auth-пользователя автоматически удаляет и `trainer_accounts` (не оставляет сироту).
- **Остаточный риск:** нет, обеспечено FK на уровне схемы (migration 011, не изменялось).

### 4.12 Изменение клуба тренера
- **Сценарий:** `trainers.club_id` меняется напрямую (SQL/Studio) без синхронизации `trainer_accounts.club_id`.
- **Вероятность:** низкая — в JCL_Gruppen сейчас НЕТ UI для смены клуба существующего тренера (форма редактирования не содержит выбор клуба); достижимо только прямым SQL.
- **Влияние:** `trainer_accounts.club_id` устаревает, `trainer_has_active_account`/`trainer_has_any_account` (фильтруют по обоим club_id) перестают находить аккаунт → тренер ошибочно откатывается на "как будто не мигрирован".
- **Защита:** триггер `enforce_trainer_accounts_club_match` (migration 011) защищает согласованность ТОЛЬКО в момент записи в `trainer_accounts`, не реагирует на изменение `trainers.club_id`后.
- **Остаточный риск:** известный, предсуществующий (migration 011, вне файлов этого диффа) архитектурный пробел.
- **Рекомендация:** не исправлялось в этой сессии (нет UI-пути, нет файла в объёме ревью) — задокументировать как ограничение; при появлении функции "перенос тренера между клубами" — синхронизировать `trainer_accounts.club_id` в той же транзакции.

### 4.13 Изменение роли администратора (Admin → Trainer)
- **Сценарий:** роль понижается, пока у администратора есть активная сессия.
- **Защита:** `manage-trainer-account` перечитывает `trainers.rolle` из БД при КАЖДОМ вызове — следующий вызов получает 403.
- **Остаточный риск:** нет — согласуется с 4.6 (fresh-check на каждый вызов).

### 4.14 Удаление тренера
- **Сценарий:** попытка удалить строку `trainers`, на которую ссылается активный `trainer_accounts`.
- **Защита:** FK `trainer_accounts.trainer_row_id REFERENCES trainers(id) ON DELETE RESTRICT` — удаление блокируется на уровне БД, пока существует связанный `trainer_accounts`.
- **Остаточный риск:** нет, структурная защита (migration 011, не изменялось).

### 4.15 Компрометация `service_role`
- **Сценарий:** утечка `SUPABASE_SERVICE_ROLE_KEY` (например, из логов CI/CD или неправильно настроенного секрета).
- **Вероятность:** низкая при соблюдении практик (`supabase secrets set`, никогда в git/frontend), но критична при реализации.
- **Влияние:** полный обход всех проверок этой функции — прямой доступ к любой таблице/Auth Admin API.
- **Защита:** ключ существует только как переменная окружения Edge Function на стороне Supabase, никогда не логируется, не возвращается в ответах, не встраивается во frontend (проверено сканированием секретов).
- **Остаточный риск:** организационный (ротация ключа, доступ к Dashboard/CI) — вне технического объёма этой сессии.
- **Рекомендация:** зафиксировать в runbook процедуру ротации `service_role` как часть общих операционных практик владельца.

### 4.16 Утечка логов
- **Сценарий:** `console.error` на фронте или логи Edge Function содержат чувствительные данные.
- **Защита:** пароль никогда не логируется (проверено построчно); `result.details` (может содержать сырые сообщения Postgres/GoTrue) выводится ТОЛЬКО в `console.error` браузера разработчика, не показывается пользователю и не отправляется на внешний сервис; аудит-лог хранит только ID и тип операции, без email/пароля/JWT.
- **Остаточный риск:** сообщения Postgres/GoTrue об ошибках теоретически могут содержать служебные детали схемы (не пользовательские секреты) — приемлемо для внутренней диагностики.

### 4.17 Rollback после частичного сбоя (DB ↔ Auth рассинхрон)
- **Сценарий:** `rename_trainer_login` в БД успешен, но `updateUserById` (email) в Auth падает.
- **Найдено и исправлено в этой сессии:** компенсирующий откат — при неудаче обновления email функция пытается вернуть `login_name` обратно; если и это падает — явная ошибка `auth_email_update_failed_and_rollback_failed` вместо тихого рассинхрона.
- **Остаточный риск:** двойной сбой (email update падает И компенсирующий rename тоже падает) технически возможен — в этом случае функция явно сообщает о необходимости ручного вмешательства, не маскирует проблему.

## 5. Явно зафиксировано (по требованию задания)

- **Frontend НЕ является доверенной зоной.** Любое состояние в браузере (роль, clubId, DOM) может быть подделано; единственная граница доверия — серверные проверки в Edge Function по JWT + fresh DB reads.
- **`anon key` НЕ является административным секретом.** Он публичен по дизайну Supabase (используется в любом клиентском JS), не даёт прав без прохождения RLS/RPC-грантов; путать его с `service_role` — ошибка, которую предыдущая (уже исправленная) shared-secret модель не допускала архитектурно, но сейчас важно не повторить в других частях системы.
- **`service_role` никогда не должен попадать во frontend.** Подтверждено сканированием — используется только внутри Edge Function на стороне сервера.
- **Первый администратор создаётся отдельным bootstrap-процессом**, не через `manage-trainer-account` (функция принципиально требует уже существующего активного администратора для своего вызова — см. `TRAINER_AUTH_PRODUCTION_RUNBOOK.md`, раздел Bootstrap).
